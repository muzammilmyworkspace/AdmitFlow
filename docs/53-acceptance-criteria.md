## 1. Purpose and Format

Every criterion below follows the exact Given/When/Then pattern established for this platform's most load-bearing rule: *"Given a student without TARGET entitlement, when they request assessment results, then only the allowed target records are returned, and locked university identity/details are not present in the API payload."* Each criterion is concrete and independently testable — it names the actor, the exact triggering action, and an observable, checkable outcome (an HTTP status, a specific field's presence/absence, a DB row count, or an audit log entry) rather than a vague behavioral description. These criteria are the acceptance bar for the corresponding `35-testing-strategy.md` and `36-security-testing.md` test implementations, not a separate, looser standard.

## 2. Entitlement / Paywall Enforcement

1. **Given** a student without a TARGET/SAFE entitlement, **when** they request `GET /api/v1/assessment/results`, **then** REACH matches are returned in full and locked TARGET/SAFE records are represented only by a count/teaser — no locked record's `universityId`, `universityName`, `programId`, `programName`, or `feeAmount` is present anywhere in the response body.
2. **Given** a student with an entitlement scoped to only a subset of TARGET matches (per-assessment or per-university-set scoping), **when** they request assessment results, **then** the specifically entitled matches are returned in full, and every other TARGET/SAFE match not covered by that entitlement remains fully omitted, not partially shown.
3. **Given** a student whose entitlement has expired (`Entitlement.status = EXPIRED`, `expiresAt` in the past), **when** they request assessment results, **then** the previously-unlocked matches are treated as locked again — the response omits their identifying fields exactly as if no entitlement had ever existed, and the student sees a re-purchase/renewal prompt rather than stale cached full detail.
4. **Given** a student who completes a purchase for a TARGET/SAFE unlock, **when** the entitlement-granting webhook has been processed and they immediately re-request assessment results, **then** the newly-entitled matches are returned in full without requiring a logout/login or manual cache clear, and no other still-locked matches are affected.
5. **Given** a non-entitled student, **when** they append undocumented query parameters (`?fields=all`, `?includeAll=true`, `?filter[zone]=TARGET`) or a debug header to the results request, **then** the response shaping is unaffected — locked fields remain fully omitted regardless of any parameter or header combination.

## 3. Payment Webhook Processing

1. **Given** a Stripe/PayPal webhook with a valid signature and a `providerEventId` never seen before, **when** it is delivered to the webhook endpoint, **then** the event is persisted to `WebhookEvent`, a `payments.reconcile` job is enqueued, the corresponding `Entitlement`/`Booking` confirmation/`Application` fee-paid state is granted atomically with the `Payment` record update, and the endpoint returns `2xx` within the provider's timeout window.
2. **Given** a webhook request with an invalid or missing signature, **when** it is delivered, **then** the request is rejected with `WEBHOOK_SIGNATURE_INVALID` (400) before any row is written to `WebhookEvent`, and no business logic (entitlement grant, notification send) is triggered.
3. **Given** a webhook event whose `providerEventId` has already been successfully processed, **when** the identical event is delivered a second time (immediately or after a delay, simulating provider retry behavior), **then** the endpoint returns `2xx` again, but zero additional side effects occur — no second `Entitlement` row, no second confirmation email, no change to any already-settled `Payment`/`Booking`/`Application` state — and this is enforced by the DB-level unique constraint on `(webhookProvider, providerEventId)`, not an application-level pre-check alone.
4. **Given** two delivery attempts for the same `providerEventId` arriving concurrently (a true race, not sequential), **when** both are processed at nearly the same instant, **then** exactly one results in a successful insert into `WebhookEvent`, the other fails the unique constraint and is handled as "already processed" without surfacing an unhandled error to the provider, and exactly one set of business-logic side effects occurs.
5. **Given** a `charge.refunded` event that arrives before its corresponding `payment_intent.succeeded` event for the same logical payment (out-of-order/redelivered), **when** both events are eventually processed regardless of order, **then** the final `Payment`/`Entitlement` state is identical and correct whether the events arrive in order A-then-B or B-then-A — no inconsistent intermediate state is ever persisted as final.

## 4. Document Vault Access Control

1. **Given** a document owned by Student A, **when** Student B (authenticated, valid session) requests `GET /api/v1/vault/documents/{A's documentId}/download-authorization`, **then** the request is denied with `404 NOT_FOUND` (not `403`, which would confirm the document's existence to B), and no signed URL is generated.
2. **Given** a signed download URL legitimately minted for a specific document version, **when** the same URL is replayed after its documented TTL (60–120 seconds) has elapsed, **then** S3 itself rejects the request — the expired signature is not honored regardless of who holds the URL.
3. **Given** a document in the `PENDING_REVIEW` state, **when** the assigned reviewer (ADMIN) approves it without also being required to supply a reason, **then** the transition to `VERIFIED` succeeds (no reason required for approval); **when** the same reviewer attempts to reject it without supplying a reason code, **then** the request is rejected server-side (400) — rejection reason is mandatory and enforced at the API layer, not only as a UI hint.
4. **Given** a document that has been quarantined after a malware-scan `infected` verdict, **when** any actor, including ADMIN, requests it through the normal vault download-authorization endpoint, **then** the request is denied and no signed URL is issued — only a separate, distinctly-permissioned security-tooling path can retrieve a quarantined object, and doing so produces its own audit entry.
5. **Given** a Consultant with a booking-scoped document share for Student C, **when** the booking's access window has elapsed, **then** a subsequent request for that same document by the same Consultant is denied, even though it succeeded before the window closed.

## 5. Application Submission Readiness Gating

1. **Given** an application in `DRAFT` status missing one or more required, category-appropriate `VERIFIED` documents, **when** the student attempts to submit it, **then** the submission is rejected with a specific list of the missing/not-yet-verified requirements, and no `SUBMITTED` transition, snapshot creation, or fee charge occurs.
2. **Given** an application in `DRAFT` status with every required document in `VERIFIED` state and all required profile/questionnaire fields complete, **when** the student submits it, **then** the transition to `SUBMITTED` occurs atomically with the creation of `ApplicationProfileSnapshot`, `ApplicationDocumentSnapshot`, `ProgramSnapshot`, and `RequirementSnapshot` rows, an `ApplicationStatusHistory` entry, and exactly one application-fee charge — all in a single transaction such that any failure partway through leaves no partial state (no `SUBMITTED` status without a complete snapshot set).
3. **Given** an application that has already reached `SUBMITTED`, **when** a second submission request is sent using the same idempotency key (double-click/two-tab replay), **then** the response is the original success response replayed idempotently — no second snapshot set, no second fee charge, and the DB-level idempotency-key uniqueness constraint is what prevents the duplicate, verified independent of request timing.
4. **Given** an application already in `SUBMITTED` status, **when** the student attempts to withdraw it via the withdrawal endpoint, **then** the request is rejected — withdrawal is only a legal transition from `DRAFT`, per the state machine, and post-submission cancellation (if ever offered) requires a distinct, support-initiated flow, not the student-facing withdraw action.
5. **Given** a document referenced by an already-submitted application later becomes `EXPIRED` or is replaced by a new version, **when** the student or an observer inspects the submitted application, **then** the application's `ApplicationDocumentSnapshot` continues to reflect exactly what was submitted at the time of submission, unaffected by the document's subsequent live-state changes.

## 6. Consultation Booking Concurrency (Double-Booking Prevention)

1. **Given** a single-capacity `AvailabilitySlot` with no existing booking, **when** two students issue booking requests for that exact slot at effectively the same instant (concurrent transactions, not sequential requests), **then** exactly one booking reaches `CONFIRMED`/`PENDING_PAYMENT`, the other receives `409 CONFLICT`, and this outcome is guaranteed by the DB-level unique constraint on `(consultantId, startsAt)` (or `slotId`) — not solely by the application-level `SELECT ... FOR UPDATE` lock, which is verified to be a belt-and-suspenders layer, not the only backstop.
2. **Given** the same single-capacity slot under a stress scenario of N (e.g., 20) simultaneous booking requests, **when** all N resolve, **then** exactly one `CONFIRMED`/`PENDING_PAYMENT` row exists for that slot, regardless of N.
3. **Given** a booking in `PENDING_PAYMENT` status, **when** its payment-hold window expires with no confirmed payment, **then** the booking transitions to `CANCELLED` and the slot becomes available for a new booking attempt — a `PENDING_PAYMENT` booking never holds a slot indefinitely.
4. **Given** a `CONFIRMED` booking within the defined cancellation window, **when** the student cancels it, **then** the slot is released and immediately bookable by another student; **given** the same booking outside the cancellation window, **when** the student attempts to cancel it through the self-service endpoint, **then** the request is denied or routed to an admin-override path (per the documented cancellation policy), never silently allowed to bypass the window.

## 7. Account Lifecycle Transitions

1. **Given** a freshly created account with `EMAIL_UNVERIFIED` status, **when** the student attempts to access any onboarding-gated feature (starting the questionnaire, viewing assessment results, uploading a document) directly by URL/API call, **then** the request is denied with `EMAIL_NOT_VERIFIED` (403), regardless of frontend routing — the gate is enforced server-side on the API, not only by hiding a UI link.
2. **Given** a valid, time-limited email-verification token, **when** it is consumed successfully, **then** the account transitions `EMAIL_UNVERIFIED → VERIFIED` exactly once, and a second attempt to consume the same token fails (single-use) without altering the already-verified account's state.
3. **Given** an account whose session has been explicitly revoked (logout, revoke-all-sessions after a password reset, or an Admin-initiated deactivation), **when** a request is made using that now-revoked session token/cookie, **then** the request is denied with `401 UNAUTHENTICATED` on the very next request — no grace period, no stale Redis-cached validity is honored past its documented short TTL.
4. **Given** a student account that has been soft-deleted/anonymized via a data-subject deletion request, **when** any subsequent request is made using that account's former credentials, **then** authentication fails, and any `Payment`, `AuditLog`, or snapshot row that references the now-anonymized `User.id` remains fully intact and queryable via its FK, unaffected by the anonymization of the `User` row's PII fields.
5. **Given** a password-reset flow completed successfully, **when** the reset finishes, **then** every other active session for that account is invalidated immediately (not just the session that performed the reset), so a session an attacker held on a compromised account does not survive a legitimate owner's remediation.

## 8. Admin Override Auditing

1. **Given** an ADMIN grants a manual entitlement override (e.g., a goodwill unlock for a payment that failed to reconcile automatically), **when** the grant request is submitted without a `reason` field, **then** the request is rejected server-side (400) before any `Entitlement` row is created — a reason is mandatory, not an optional UI field.
2. **Given** an ADMIN grants a manual entitlement override with a valid reason, **when** the grant succeeds, **then** an `AuditLog` entry is created in the same transaction as the `Entitlement` row, recording the actor's identity, the action code, the reason text, the affected student/resource id, and a timestamp — and if the transaction fails for any reason, neither the `Entitlement` row nor the `AuditLog` entry exists (no state change without its audit record, ever).
3. **Given** an ADMIN or SUPER_ADMIN rejects a document with a required reason code, updates an application's status on a university's behalf, or revokes an entitlement post-refund, **when** each of these actions completes, **then** each produces its own distinct `AuditLog`/`DocumentAuditLog`/`ApplicationStatusHistory` entry attributing the specific actor and reason — a single admin session performing multiple override actions in sequence produces one audit entry per action, never a single batched entry that obscures which specific action did what.
4. **Given** a SUPER_ADMIN views a specific student's private document content directly (not just a listing), **when** that access occurs, **then** it is logged with the same rigor as an ADMIN's equivalent access (`document.download_authorized`) — "Super Admin" grants broader reach, not exemption from logging.
5. **Given** an ADMIN account's role/permissions are revoked or downgraded mid-session by a SUPER_ADMIN, **when** the now-downgraded admin's existing session attempts a privileged action that requires the removed permission, **then** the action is denied at the new, lower privilege level on the very next request, and the (failed) attempt itself is still logged as an authorization-denial event distinct from a successful audited override.
