## 1. Purpose

This is the concrete, testable security test catalog for AdmitFlow — not a general security checklist, but the specific attack scenarios this platform's architecture must defend against, each written so an engineer or an automated test can implement it directly: attack steps, expected secure behavior, and the exact response/log/DB signal that proves pass or fail. Per `35-testing-strategy.md` §8, this catalog is a required, blocking CI gate on any pull request touching an authorization, payment, webhook, document, or booking code path — it is not exploratory pentesting, it is regression testing for known, named invariants.

**Test-naming convention:** every test in this catalog has a stable ID (`SEC-<category>-<number>`) referenced from code (`describe('SEC-IDOR-01: ...')` or equivalent) so a failing CI check maps directly back to the row in this document that explains *why* the test exists, not just what assertion failed.

## 2. Category: Insecure Direct Object Reference (IDOR)

**Threat:** a valid, authenticated session belonging to User A is used with a resource ID belonging to User B, obtained by guessing, incrementing, enumerating, or otherwise not through a legitimate share/grant. Per `02-personas-and-roles.md` §7, UUIDs are defense-in-depth only — every one of these tests must pass even if the attacker somehow has a *real, valid* UUID for another user's resource (e.g., leaked in a support ticket, a screenshot, a referrer header), not just a guessed one.

| ID | Scenario | Attack steps | Expected secure behavior | Pass signal | Fail signal |
|---|---|---|---|---|---|
| SEC-IDOR-01 | Profile access | Student A authenticates; requests `GET /api/v1/profiles/{studentB's profileId}` | Request denied | `404 NOT_FOUND` (per `11-api-architecture.md` §10 — never `403`, which would confirm existence); zero profile fields in response body | `200` with any of B's data, or a `403` that still leaks existence |
| SEC-IDOR-02 | Document metadata/content access | Student A requests `GET /api/v1/vault/documents/{studentB's documentId}` and `GET /api/v1/vault/documents/{documentId}/download-authorization` | Both denied; no signed URL minted | `404`; assert zero calls made to the S3 signed-URL-minting function (mock/spy assertion in the integration test, not just the HTTP response) | Any signed URL returned, or the minting function invoked at all |
| SEC-IDOR-03 | Assessment result access | Student A requests `GET /api/v1/assessment/results/{studentB's assessmentResultId}` | Denied | `404`; zero assessment fields (locked or unlocked) present | `200` with any REACH/TARGET/SAFE data belonging to B |
| SEC-IDOR-04 | Application access | Student A requests `GET /api/v1/applications/{studentB's applicationId}` and attempts `PATCH` (e.g., withdraw) against it | Both denied | `404` on GET; `404` on PATCH (not `403`, not a silent no-op `200`); DB row for B's application unchanged (assert via direct query) | `200` on either, or B's application row mutated |
| SEC-IDOR-05 | Payment/receipt access | Student A requests `GET /api/v1/payments/{studentB's paymentId}` | Denied | `404`; zero payment/amount/card-brand-last4/receipt fields present | Any payment metadata belonging to B returned |
| SEC-IDOR-06 | Booking access | Student A requests `GET /api/v1/consultation/bookings/{studentB's bookingId}`, including any session notes or shared documents attached to that booking | Denied | `404`; zero booking fields, zero shared-document references | Any of B's booking/session data returned |
| SEC-IDOR-07 | Sequential/enumerated ID sweep | Automated script issues 200 sequential/randomly-sampled UUID lookups against each of the above endpoints using a single valid Student A session | Every non-owned lookup denied uniformly; the sweep itself is detectable | Zero successful non-owned reads across the sweep; sweep pattern (high 404 rate from one session in a short window) is asserted to produce an anomaly-log/rate-limit signal (ties to `47-rate-limiting.md`) | Any non-owned read succeeds, or the sweep produces no anomaly signal at all |

## 3. Category: Role Escalation

**Threat:** a valid session for a lower-privilege role is used to invoke an endpoint or action scoped to a higher-privilege role, or a role is used outside its legitimate scope boundary (a Consultant reaching outside their own bookings).

| ID | Scenario | Attack steps | Expected secure behavior | Pass signal | Fail signal |
|---|---|---|---|---|---|
| SEC-ROLE-01 | Student calls Admin-only endpoint | STUDENT session calls `POST /api/v1/admin/documents/{id}/verify`, `POST /api/v1/admin/entitlements/grant`, `GET /api/v1/admin/audit-logs` | All denied | `403 FORBIDDEN` on every call; zero side effects (no document state change, no entitlement created, no audit rows returned) | Any `200`, or any partial side effect despite an error response |
| SEC-ROLE-02 | Student calls Super-Admin-only endpoint | STUDENT session calls pricing configuration (`PATCH /api/v1/billing/prices/{id}`) and scoring-rule publish endpoints | Denied | `403`; `Price`/`AssessmentRule` rows unchanged | Any mutation succeeds |
| SEC-ROLE-03 | Consultant accesses another consultant's bookings | Consultant A session calls `GET /api/v1/consultation/bookings?consultantId={B}` or `GET /api/v1/consultation/bookings/{B's bookingId}` | Denied | `404` (per object-level rule) on the specific booking; a list-filter attempt is either scoped server-side to force `consultantId = A` regardless of the query param (ignoring/overriding a client-supplied `consultantId` that isn't the caller's own) or rejected — never trusts a client-supplied actor-identifying filter param | Any of B's booking data returned to A |
| SEC-ROLE-04 | Consultant attempts write outside their scope | Consultant session attempts `PATCH` on a student's profile, document, application, or entitlement | Denied | `403`; no row mutated — Consultants have no write path to any of these resources under any circumstance (`02-personas-and-roles.md` §3) | Any successful mutation |
| SEC-ROLE-05 | Admin attempts Super-Admin-exclusive action | ADMIN session attempts to create/deactivate another ADMIN account or assign a role | Denied | `403`; `User`/`UserRole` rows unchanged | Any role assignment or admin-account mutation succeeds |
| SEC-ROLE-06 | Privilege escalation via request body tampering | STUDENT session submits a signup/profile-update/any mutable payload with an injected `role: "ADMIN"`, `permissions: [...]`, or `isAdmin: true` field not part of the endpoint's schema | Field is rejected or silently stripped by schema validation before it ever reaches business logic | The resulting `User`/`Session` row's role is unchanged from `STUDENT`; a strict-schema validator test asserts unknown/forbidden fields are dropped, not merged | Role or permission field on the record changes as a result of the tampered payload |
| SEC-ROLE-07 | Expired/downgraded role, cached session | An Admin's role is revoked/downgraded mid-session (e.g., deactivated by Super Admin) | The very next request using that session is denied at the new, lower privilege level | `403` on the next privileged call; assert no stale-role cache (Redis session cache) is trusted for authorization decisions past a short, documented TTL — see `13-authentication-authorization.md` | A revoked Admin retains privileged access for longer than the documented cache TTL |

## 4. Category: Locked University/Program Data Leakage (Critical — Named Invariant)

**This is the platform's single most critical data-leakage class and has the highest bar in this catalog: the test must inspect the literal HTTP response body bytes, never the rendered UI.** Per `01-product-requirements.md` §6 and `11-api-architecture.md` §10, locked TARGET/SAFE content — university identity, name, program name/id, fee, and any other identifying metadata — must be **omitted from the JSON entirely**, not nulled, not blurred, not sent-then-hidden.

| ID | Scenario | Attack steps | Expected secure behavior | Pass signal | Fail signal |
|---|---|---|---|---|---|
| SEC-LEAK-01 | Non-entitled student requests assessment results | Student with zero TARGET/SAFE entitlements calls `GET /api/v1/assessment/results/{id}` | REACH matches returned in full; TARGET/SAFE matches represented only as a count/teaser | Deep key-enumeration of the parsed JSON response confirms **no key path anywhere in the payload** contains `universityId`, `universityName`, `programId`, `programName`, `feeAmount`, `tuition`, or any other university/program-identifying field for a locked record — asserted programmatically (recursive object-key walk against a denylist), not by checking a specific expected field name that a future renamed field could slip past | Any locked identifying field present under any key, including a nested/renamed one the denylist walk is written broadly enough to catch (e.g., `_debugUniversityName`, `matchedProgram.name`) |
| SEC-LEAK-02 | Partial entitlement (some but not all locked matches purchased) | Student with an entitlement scoped to a subset of TARGET matches (per-assessment or per-university-set scoping) requests results | Only the specifically entitled matches' full detail is present; remaining locked matches still fully omitted | Same recursive-denylist assertion, run against the specific still-locked subset only | Any still-locked match's identifying fields present |
| SEC-LEAK-03 | Query/filter/sort manipulation attempting to bypass shaping | Non-entitled student adds `?filter[zone]=TARGET`, `?sort=universityName`, `?fields=all`, or any undocumented query param to the results endpoint | Shaping logic is applied identically regardless of query params — filtering/sorting/field-selection operates only on the already-shaped (locked-fields-omitted) result set, never on the pre-shaping full record set | No combination of query params surfaces a locked field; an unrecognized `fields`/`sort` param either is ignored safely or returns `VALIDATION_ERROR`, never a bypass | Any query parameter combination causes a locked field to appear |
| SEC-LEAK-04 | Admin-debug / support-tooling flag bypass | A request carrying any internal debug header or flag (e.g., `X-Debug: true`, `?includeAll=true`) that isn't a documented, permission-gated Admin API | Ignored for a STUDENT-scoped request; no code path exists where a debug flag re-adds omitted fields for a non-privileged caller | No locked field appears regardless of header/flag combination attempted | A debug flag reveals locked content to a STUDENT session |
| SEC-LEAK-05 | Response-shaping regression via list/detail endpoint divergence | Compare the shaped output of the list endpoint (`GET /api/v1/assessment/results`) against the detail endpoint for one result (`GET /api/v1/assessment/results/{id}`) for the same non-entitled student | Both endpoints omit locked fields identically — no endpoint is "less careful" than another for the same underlying data | Recursive denylist assertion passes against both endpoints' raw bodies | Either endpoint leaks a field the other correctly omits |
| SEC-LEAK-06 | Post-purchase field reveal correctness (negative-of-negative check) | Student purchases entitlement, immediately re-requests results | Previously-locked fields for the now-entitled scope are now present and correct (this test exists so the omission logic is never over-corrected into permanently hiding data the student has legitimately paid for) | Full expected fields present for the newly-entitled scope; still-locked (unpurchased) scopes still pass SEC-LEAK-01's assertion | Newly-entitled data still omitted, or the omission check is failing open in a way that also happens to hide legitimate data |

**Decision:** the recursive denylist walk used in SEC-LEAK-01 through 06 is implemented once, as a shared test-utility function (`assertNoLockedFieldsPresent(responseBody, lockedRecordIds)`), reused by every test in this section and by the corresponding E2E network-inspection test in `35-testing-strategy.md` §6 item 4 — not reimplemented per test, so a denylist improvement (a newly added field name) automatically strengthens every consumer.

## 5. Category: Document / Signed-URL Leakage

These restate and extend `15-document-vault-security.md` §10's required tests with explicit pass/fail signals; that section remains the authoritative source for the vault-specific rationale.

| ID | Scenario | Attack steps | Expected secure behavior | Pass signal | Fail signal |
|---|---|---|---|---|---|
| SEC-DOC-01 | Signed URL used by a different user | User B somehow obtains a signed download URL legitimately minted for User A's document (e.g., captured from a shared screenshot/log) and issues the raw GET directly against S3, bypassing the app entirely | S3 itself serves the object if the signature is valid and unexpired — the control here is that the signature is scoped to exactly one object key, never a prefix; the actual defense is that B can never get a *signed URL* for their own or a third user's document through the app that reveals A's key | Confirm the signed URL's scope is a single object key (not a wildcard/prefix policy) by inspecting the generated URL/policy in the test; confirm the app-level download-authorization endpoint never returns A's key to B under any request shape | A signed URL is generated with prefix or wildcard scope, or the app-level endpoint leaks another user's key/URL |
| SEC-DOC-02 | Signed URL replayed after expiry | Capture a valid signed GET/PUT URL, wait past its documented TTL (60–120s per `15-document-vault-security.md` §2), replay it | S3 rejects the expired signature | HTTP 403 (or provider-equivalent) from S3 on replay; assert this is enforced at the storage layer, not merely assumed — the test actually waits out the TTL (or uses a provider clock-skew/short-TTL test fixture) rather than mocking "expired" | Replay succeeds after TTL |
| SEC-DOC-03 | Direct S3 key guessing | Attempt to construct/guess an object key (`vault/{userId}/{documentId}/{version}`) for a known or brute-forced `userId`/`documentId` pair and request it directly from S3 without ever going through the app | Bucket denies all public access; unsigned/guessed-key requests fail regardless of correctness of the guess | S3 returns access-denied for any unsigned request, verified against the bucket policy configuration itself (a policy assertion test, not just a runtime probe) | Any unsigned direct S3 request succeeds |
| SEC-DOC-04 | Quarantine isolation | Any role, including ADMIN, requests download-authorization for an object under the `quarantine/` prefix via the normal vault endpoint | Denied via the standard vault path regardless of role | `404`/`403` from the normal endpoint for every role; only a separate, distinctly-permissioned security-tooling path can retrieve it, and doing so is itself audit-logged | Normal vault endpoint issues any signed URL for a quarantined object, for any role |
| SEC-DOC-05 | Malicious file upload — EICAR | Upload the standard EICAR test string under every document category | Caught by the scan step, quarantined, `document.malware_detected` audit entry written, never reaches `PENDING_REVIEW` | Document row lands in `REJECTED`; quarantine object exists; audit log entry present with scan-engine/signature metadata and zero file-content in the payload | Document reaches `PENDING_REVIEW`/`VERIFIED`, or is silently deleted with no audit trail |
| SEC-DOC-06 | Oversized file | Upload bypassing the declared pre-flight size check (declare a small size, send a larger real payload) | Rejected at the storage-layer content-length condition and/or the worker's authoritative real-byte-size check | Object either fails to PUT at S3, or is caught by the worker and transitions to `REJECTED`; never reaches `PENDING_REVIEW` | Oversized real file reaches `PENDING_REVIEW` |
| SEC-DOC-07 | Mismatched extension/MIME vs. real magic bytes | Upload a file renamed with an allowed extension (e.g., `.pdf`) whose real magic bytes are a disallowed/different type (e.g., an executable or script) | Rejected with `invalid_or_unrecognized_file_type`, never accepted on declared extension/Content-Type alone | `REJECTED` with the specific reason code; `document.type_mismatch_detected` audit entry present | Accepted based on filename/declared type |
| SEC-DOC-08 | Executable disguised as a document | Upload a native executable (PE/ELF/Mach-O header) or a script with a document-category extension | Rejected outright at magic-byte validation | `REJECTED`, `invalid_or_unrecognized_file_type`; malware scan is still run regardless (defense in depth, per `15-document-vault-security.md` §5's "scan every format" decision) even though type validation should already have caught it | Accepted, or scan step skipped because type validation already failed (both checks must independently run) |
| SEC-DOC-09 | Zip-bomb-style file | Upload a maliciously-crafted archive/DOCX designed to expand to an enormous size or exhaust worker resources during scanning/parsing | Worker enforces a bounded decompression/parse limit and treats exceeding it as `invalid_or_unrecognized_file_type` or `scan_error` (fail-closed), never lets the worker process hang or OOM | Job fails safely within a bounded time/memory budget; document `REJECTED`; worker process/pod remains healthy for the next job (no crash-loop) | Worker process crashes, hangs, or OOMs; or the file is silently accepted |

## 6. Category: Payment Manipulation

| ID | Scenario | Attack steps | Expected secure behavior | Pass signal | Fail signal |
|---|---|---|---|---|---|
| SEC-PAY-01 | Client-supplied amount tampering (unlock purchase) | Client sends a checkout-session-creation or payment-confirmation request with a lower `amount` than the real `Price` record | Server re-derives the amount from the authoritative `Price` record server-side and ignores/rejects the client value | Request rejected (`VALIDATION_ERROR` or equivalent) if the endpoint even accepts a client-supplied amount at all — **preferred implementation is that the endpoint never accepts a client-supplied amount in the first place**, only a `priceId`/`productId` reference, making this class of tampering structurally impossible rather than merely checked; the test asserts whichever is actually implemented never results in a charge below the real price | Any charge or entitlement grant at less than the real price |
| SEC-PAY-02 | Client-supplied amount tampering (higher) | Client sends an inflated `amount` | Rejected identically — an inflated client-supplied value is still evidence the client isn't authoritative and is rejected, not "accepted because it favors the platform" | Same as above, request rejected/ignored | A charge is created using the client-supplied inflated amount rather than the server-derived one |
| SEC-PAY-03 | Currency tampering | Client requests checkout in a currency that doesn't match the `Price` record's configured currency | Rejected | `VALIDATION_ERROR`; checkout session created (if at all) only in the server-known currency | Checkout proceeds in a client-chosen mismatched currency |
| SEC-PAY-04 | Client-reported success without provider confirmation | Client calls a hypothetical "mark as paid" endpoint or manipulates frontend state to display "unlocked" without a real completed payment | No entitlement is ever granted by any client-facing call — entitlement grant is reachable *only* from the webhook-reconciliation code path, per `09-database-architecture.md` §7's Payment→Entitlement transaction | Static/integration test confirms there is no API route capable of granting an `Entitlement` row that is reachable from a STUDENT-authenticated request — grant is only invoked from the worker's webhook-reconciliation job | Any student-reachable endpoint can create/activate an `Entitlement` row |
| SEC-PAY-05 | Stale/superseded price race | A `Price` is deactivated/changed between checkout-session creation and webhook confirmation | Reconciliation uses the amount actually confirmed by the provider for that specific transaction, never a live re-lookup of current pricing at reconciliation time | Entitlement granted matches what was actually paid for the locked-in quote, regardless of subsequent price changes | Entitlement scope/amount recorded reflects a price that changed after checkout began |
| SEC-PAY-06 | Downgrade/tamper on application-fee or booking payment | Same class of amount/currency tampering attempted against the application-fee and consultation-booking payment paths, not just the unlock-purchase path | Identical re-derivation-and-reject behavior | Same signals as SEC-PAY-01 through 03, run against both additional payment contexts | Any of the three payment contexts (unlock, application fee, booking) has weaker validation than the others |

## 7. Category: Webhook Replay and Ordering

| ID | Scenario | Attack steps | Expected secure behavior | Pass signal | Fail signal |
|---|---|---|---|---|---|
| SEC-WEBHOOK-01 | Exact duplicate delivery | The identical webhook payload (same `providerEventId`) delivered twice, back to back | Second delivery is a no-op for business logic; both return `2xx` | Row count for `Entitlement`/`Payment`/notification-send unchanged between delivery 1 and delivery 2; `WebhookEvent` unique constraint on `(webhookProvider, providerEventId)` is the mechanism verified directly — the test asserts the constraint exists and is what prevents the duplicate insert, e.g. by checking the second insert attempt raises the DB-level unique-violation that the handler catches, not by only checking the end-to-end outcome | Two entitlement rows, two confirmation emails, or any doubled side effect; or the dedup is implemented as an app-level `SELECT-then-INSERT` check with no DB constraint backing it (race-prone even if this specific sequential test happens to pass) |
| SEC-WEBHOOK-02 | Concurrent duplicate delivery (true race) | Same `providerEventId` delivered via two simultaneous requests (not sequential — genuinely concurrent, per the full-commit integration pattern in `35-testing-strategy.md` §5) | Exactly one insert succeeds at the DB constraint; the other's insert attempt fails the unique constraint and is handled as "already processed," not as an unhandled error | One `WebhookEvent` row; no unhandled exception/500 from the losing request — it still returns `2xx` to the provider after detecting the constraint violation gracefully | Both requests report success with divergent side effects, or the losing request surfaces a `500`/unhandled error to the provider (which would trigger further provider retries) |
| SEC-WEBHOOK-03 | Signature forgery | A request to the webhook endpoint with a well-formed provider-shaped payload but an invalid/missing/forged signature header | Rejected before any processing | `400 WEBHOOK_SIGNATURE_INVALID`; zero rows written to `WebhookEvent`, zero business logic invoked (verified by spy/mock on the reconciliation function, asserting it is never called) | Any processing occurs, or a `WebhookEvent` row is written despite the invalid signature |
| SEC-WEBHOOK-04 | Out-of-order delivery | `charge.refunded` arrives before `payment_intent.succeeded` for the same logical payment (simulating provider redelivery/network reordering) | Reconciliation logic sequences based on persisted record state, not delivery order; the refund event is deferred/retried until its prerequisite exists, or is otherwise handled without producing an inconsistent state | Final state after both events have been processed (in either order) is identical and correct — asserted by running the test both ways (A-then-B and B-then-A) and diffing the resulting `Payment`/`Entitlement` state, which must be identical | Final state differs depending on delivery order, or an event is dropped/errors out because its prerequisite hadn't arrived yet |
| SEC-WEBHOOK-05 | Replay from a different, unrelated provider event stream | A `providerEventId` value is reused (accidentally or adversarially) across what should be logically distinct events (e.g., same ID string generated by a malformed test/staging integration) | Uniqueness constraint is scoped to `(webhookProvider, providerEventId)` composite, correctly distinguishing provider namespaces, so a Stripe and a PayPal event never collide even with coincidentally identical ID strings | Both events process independently and correctly when using different `webhookProvider` values with the same `providerEventId` string | A collision across providers incorrectly suppresses processing of the second, legitimate event |

## 10. Category: Rate-Limit Bypass Attempts

| ID | Scenario | Attack steps | Expected secure behavior | Pass signal | Fail signal |
|---|---|---|---|---|---|
| SEC-RATE-01 | Header spoofing | Client sends requests exceeding the documented rate limit while varying/spoofing `X-Forwarded-For`, `X-Real-IP`, or a client-supplied `X-Request-Id`/session-adjacent header across otherwise-identical requests from the same authenticated session | Rate limiting keys off the authenticated session/user identity (and/or the connection-level source, resolved server-side, never a client-controlled header) for authenticated endpoints, so header spoofing does not reset the limit | `429 RATE_LIMITED` continues to trigger at the documented threshold regardless of spoofed headers, for the same session | Spoofed headers reset or bypass the limit for the same authenticated user |

| SEC-RATE-03 | Distributed-source bypass (documented as a noted residual gap, not a claimed-solved test) | Simulate the same logical actor making requests that would appear to originate from many different IPs (conceptually — this specific test validates *detection*, not prevention, since per-IP rate limiting alone cannot structurally prevent a truly distributed attacker) | The system does not claim to fully solve this via rate limiting alone; the test instead validates that account-level/behavioral anomaly signals (e.g., unusual volume of failed logins against one account regardless of source IP diversity) are logged and alertable | An account-level threshold (e.g., N failed logins across any combination of sources in a window) still triggers a lockout/step-up-auth signal, independent of per-IP limits | No account-level backstop exists at all — the system relies solely on per-IP limiting for a threat model where that is insufficient (see `49-threat-model.md`'s residual risk section, which names this explicitly rather than claiming it's fully solved) |

## 11. Category: SQL Injection

**Structural claim under test:** because all database access goes through Prisma's parameterized query builder (`09-database-architecture.md` §2/§10 — no raw string-concatenated SQL is a permitted pattern in this codebase), classic SQL injection should be structurally impossible. This category exists to *prove that claim holds*, not to "try to find SQL injection" as if it were an open question.

| ID | Scenario | Attack steps | Expected secure behavior | Pass signal | Fail signal |
|---|---|---|---|---|---|
| SEC-SQLI-01 | Search/filter input injection | Every free-text search/filter parameter (university/program search `q`, admin user search, audit-log filters) is sent a battery of classic SQLi payloads (`' OR '1'='1`, `'; DROP TABLE users; --`, boolean-blind and time-based payloads) | Payload is treated as a literal search string; no syntax error, no behavioral difference (timing/row-count) indicating query structure was affected | Query returns zero/normal results treating the payload as literal text; no elevated error detail leaked (ties to `11-api-architecture.md` §5's "never serialize stack traces" rule — a raw DB error message appearing in a response is itself a fail signal even absent actual injection); a static-analysis/lint rule additionally scans the codebase for any raw/string-interpolated SQL call as a standing structural check, not just a runtime probe | Any behavioral evidence the payload altered query structure (error message revealing SQL syntax, timing consistent with a time-based payload succeeding, or a raw DB error in the HTTP response) |
| SEC-SQLI-02 | Injection via sort/field-selection parameters | SQLi-style payloads in `sort=`, `fields=`, and pagination `cursor=` parameters | Rejected as `VALIDATION_ERROR` (unrecognized sort field, per `11-api-architecture.md` §8) or safely ignored — never concatenated into a query | Same as above | Same as above |
| SEC-SQLI-03 | Injection via JSON/free-text fields that are later used in any raw query context (e.g., a full-text search feature over SOP content, if implemented) | Payloads injected into any field that feeds a search-indexing or raw-query code path | Same parameterization guarantee holds even for full-text search — provider-specific full-text query builders (e.g., Postgres `tsquery` construction) are also verified to escape/parameterize user input, not string-concatenate it into a `tsquery` expression | No behavioral evidence of query-structure manipulation | Any evidence of injection succeeding in a full-text or raw-query context |

## 12. Category: XSS (Cross-Site Scripting)

| ID | Scenario | Attack steps | Expected secure behavior | Pass signal | Fail signal |
|---|---|---|---|---|---|
| SEC-XSS-01 | Stored XSS via Statement of Purpose text | A student submits SOP free text containing `<script>`, an `<img onerror=...>` payload, and an encoded/obfuscated variant, then the value is rendered anywhere it's displayed (student's own view, admin review UI, any PDF/export generation) | Rendered as inert text everywhere, never executed | DOM inspection in the E2E/component test confirms the payload appears as literal text/escaped entities, not as an executed script or an active DOM attribute; a headless-browser test asserts no `alert()`/marker script actually fires | Script executes in any rendering context (student view, admin view, or export) |
| SEC-XSS-02 | Stored XSS via profile fields | Same payload battery injected into name, bio, and other free-text profile fields, checked everywhere the profile is rendered (student self-view, admin support view, consultant booking-scoped view, any notification template interpolating the name) | Same — inert everywhere, including notification emails (HTML-email templates are a common miss) | Same DOM/rendering assertion extended to the email-template rendering path (assert the rendered email HTML escapes the payload) | Execution or unescaped raw HTML in any surface, including emails |
| SEC-XSS-03 | Stored XSS via Admin notes | Payload injected into admin-authored notes/rejection-reason free text, checked in the student-facing surfaces where those notes are shown (e.g., a document rejection reason) | Inert on render to the student | Same DOM assertion | Execution when a student views an admin note containing the payload |
| SEC-XSS-04 | Reflected XSS via query parameters | Payload injected into any query parameter that is echoed back in an error message, a "no results for {query}" UI string, or similar | Escaped/encoded on render, never executed | Same DOM assertion for the specific reflected-parameter surfaces | Execution via a reflected parameter |
| SEC-XSS-05 | Content-Security-Policy backstop | Regardless of any single escaping miss, verify a restrictive CSP header is present on every HTML response (no `unsafe-inline` for scripts, no wildcard script-src) | CSP present and correctly restrictive | CSP header inspected on every route's response in an integration test; a deliberately-injected inline script is confirmed blocked by CSP even in a hypothetical escaping-miss scenario (tested by temporarily allowing the payload through and confirming the browser still refuses to execute it under the real CSP) | CSP absent, or permissive enough that an escaping miss would still execute |

## 13. Category: CSRF (Cross-Site Request Forgery)

| ID | Scenario | Attack steps | Expected secure behavior | Pass signal | Fail signal |
|---|---|---|---|---|---|
| SEC-CSRF-01 | State-changing request without CSRF protection, cookie-authenticated | A cross-origin page issues a state-changing request (e.g., `POST /api/v1/applications/{id}/submit`, `PATCH /api/v1/profiles/me`, `POST /api/v1/consultation/bookings`) relying only on the browser's automatically-attached session cookie, with no CSRF token and no matching-origin check | Rejected | `403` (or the framework's CSRF-failure equivalent) when the CSRF token is missing/invalid, or when `SameSite`/`Origin`/`Referer` validation fails, depending on which mechanism is implemented — the test asserts whichever mechanism is chosen actually blocks the cross-origin request, not merely that a token field exists in same-origin forms | Cross-origin state-changing request succeeds |
| SEC-CSRF-02 | `SameSite` cookie attribute verification | Inspect the session cookie's attributes directly | `SameSite=Lax` or `Strict` (never `None` without an accompanying, justified exception), `Secure`, `HttpOnly` all set | Cookie attributes confirmed via response header inspection in an integration test | Any of the three attributes missing/misconfigured |
| SEC-CSRF-03 | GET requests never mutate state | Audit (and test) that no state-changing operation is reachable via a `GET` request (which browsers will issue cross-origin without any CSRF friction, e.g., via an `<img>` tag) | All mutations are `POST`/`PATCH`/`PUT`/`DELETE` only | No `GET` route in the API surface produces a side effect — verified by a route-inventory test asserting every `GET` handler is read-only (no repository write calls reachable from a GET handler) | Any `GET` endpoint found to mutate state |
| SEC-CSRF-04 | Webhook endpoints are correctly exempt, but only via signature verification, never via disabling CSRF protection broadly | Confirm the Stripe/PayPal webhook routes (which cannot carry a same-origin CSRF token, since the caller is the provider, not a browser) are protected by signature verification (§7 above) rather than by a blanket CSRF exemption that could be accidentally widened to cover other routes | Webhook routes are the *only* routes exempted from the cookie-based CSRF mechanism, and that exemption is scoped narrowly (by route, not by a global flag) | A route-level audit confirms the CSRF-exemption list contains only the two webhook routes | Any non-webhook route is found in the CSRF-exemption configuration |

## 14. Reporting and Gating

- Every test in this catalog runs in CI per `35-testing-strategy.md` §8's rule (blocking gate on any PR touching an authorization, payment, webhook, document, or booking path); a full run is additionally scheduled nightly against the staging environment regardless of what changed, so a dependency or configuration drift (e.g., a CDN/WAF change accidentally weakening CSP) is caught even without a code change triggering it.
- A failure in any `SEC-LEAK-*` or `SEC-WEBHOOK-*` test is treated as a release-blocking Sev-1, not a normal bug ticket — these two categories map directly to the platform's two named critical invariants.
- Test IDs in this document are stable identifiers; renumbering is treated as a breaking change to the document (old IDs referenced in past incident reports/PRs must remain resolvable), so new tests are appended with new numbers rather than the list being renumbered.
